## 0. 方法论与口径（实验前定义，中途修正须在 §修正记录 留痕）

### 0.1 环境约束（2026-07-07 实测）

- 本机**无任何 Anthropic API 凭据**（无 `ant` CLI、无 `ANTHROPIC_API_KEY`、无 `.env`）→ 无法调用 count_tokens 端点，无法直接打 Messages API。
- 替代实验通道：**Claude Code Agent 工具可指定 haiku / sonnet / opus 模型**。本项目生产默认模型是 `claude-haiku-4-5-20251001`，与 Agent 工具的 haiku 同款 → prompt 行为类实验（输出长度、JSON 可解析性、指令遵循）在真实目标模型上可跑。
- Ollama down（embedding 不涉及 API 成本，只有本机算力/延迟成本，不在本轮 $ 口径内）。
- Docker up（如需起 Postgres 复现真实数据流可用）。

### 0.2 Token 计数口径

- **估计器 est_tokens(text)**：双通道字符估计。
  `tokens ≈ ascii_chars / 3.6 + cjk_chars × 1.0 + other_chars / 2.0`
- **绝对值不确定度 ±25%**（无法用官方 count_tokens 校准，已知偏差来源：代码/JSON 密度、混排文本）。
- **比较类结论一律用比值口径**（方案 A tokens ÷ 方案 B tokens，同一估计器下偏差大部分抵消）→ 比值结论视为可靠，绝对 $ 数字带误差条。
- 输出 token：mock 场景用 `llm_max_tokens=512` 上限与实测输出长度双口径；真实 haiku 实验用实际输出文本估计。

### 0.3 成本口径（claude-api skill 缓存表，2026-06-24）

| 模型 | Input $/MTok | Output $/MTok |
|---|---|---|
| claude-haiku-4-5（项目默认） | $1.00 | $5.00 |
| claude-sonnet-4-6 / sonnet-5 | $3.00 | $15.00 |

## 1. 实验台账

### E-01 居民 system prompt 稳定前缀尺寸 vs Haiku 缓存阈值
- 假设（实验前写）：为什么试——prompt caching 是最大的潜在节省（读 0.1×），但 Haiku 4.5 最小可缓存前缀是 4096 tokens，低于阈值会静默不缓存。观察 `assemble_system_prompt`（app/llm/prompt.py:40）稳定前缀 = 身份行 + soul_md + persona_md + ability_md。预期：dev DB 15 个居民 + 种子预置角色的稳定前缀 est_tokens **全部 < 4096**（中位数落在 300–800），即项目在 Haiku 上做 system prompt 缓存收益为零，除非（a）换 1024 阈值的模型，或（b）把 prompt 结构改造为共享大前缀。
- 方法：读 backend/skills_world_dev.db 的 residents 表，对每个居民计算 est_tokens(稳定前缀)（§0.2 估计器），输出分布。脚本：docs/research/scripts/e01_prompt_sizes.py
- 结果：n=15，min=189 / median=208 / max=908 / mean=314 est_tokens。≥4096 的 0 个；≥2048 的 0 个；≥1024 的 0 个。最大是萧炎（908，Forge 生成的长 persona），手写预置角色全部 <400。
- 状态：done
- 结论：**假设成立且比预期更极端**。当前 per-resident system prompt 距离任何在售模型的最小缓存前缀（Sonnet4.5 1024 / Fable 2048 / Haiku 4096）都差一个数量级，在 Haiku 上加 cache_control 是纯负收益（白付 1.25× 写费或静默无效）。缓存要产生收益只有一条路：**构造 >4096 tokens 的全局共享前缀**（世界观/规则/地图常识放最前面，所有居民共享），persona 放后面——这引出 E-1x「加大前缀反而省钱吗」的权衡实验（加前缀 = 每次多付未命中 input，命中后 0.1×）。
- 偏差与备注：估计器 ±25% 不影响结论（908×1.25 仍 << 4096）。dev DB 有两个重复的萧炎行。

### E-02 居民互聊 history 双重注入的浪费量化
- 假设（实验前写）：为什么试——读代码发现 `resident_chat`（app/agent/chat.py:126-138）每轮把同一段 history 字符串**同时**注入 system prompt（CHAT_REPLY_SYSTEM 的 {history} 槽）和 user message，输入被双重计费；且 system 每轮重建（说话人轮换+history 增长），跨轮缓存不可能。预期：8 轮标准对话（median persona 208 tokens、每行回复 ≈35–60 tokens、history 窗口最近 6 行）中，双注入的重复部分占总输入 tokens 的 **15–25%**；改为"history 只出现一次"的对照方案 B 可等比例省掉。
- 方法：按代码路径精确复刻 8 轮对话的每轮完整请求（system+messages），方案 A=现状双注入，方案 B=history 仅入 messages。合成回复行（中文 40 字/行，对应指令"50字以内"）。对比总 est_tokens。脚本：docs/research/scripts/e02_chat_double_history.py
- 结果：方案 A input=5477 / 方案 B input=4209 → 双注入浪费 1268 tokens = **总输入的 23.1%**（落在预测区间 15–25% 上沿）。附带发现：persona 每轮全量重复注入共 1927 tokens = 总输入的 **35.2%**。
- 状态：done
- 结论：假设成立。修法一行级：CHAT_REPLY_SYSTEM 去掉 {history} 槽或 user message 不再重复传。更大的鱼是 persona 重复（35%）——若把互聊改造成**标准多轮 messages 结构**（system 固定 = persona+关系，对话按 user/assistant 轮次追加），则 persona 只计费一次/轮但可被前缀缓存吃掉（配合 E-01 的共享大前缀方案），两项合计理论上限 ~50% 输入节省。→ 衍生实验：E-协议重构方案的净节省测算。
- 偏差与备注：合成 persona 用 241 tokens（≈真实 median 208）；真实对话回复长度有方差，比值结论稳健。

### E-03 现状 token 记账（len(full_reply)）作为成本口径的失真度
- 假设（实验前写）：为什么试——P1-1 要做计量，得先知道现状记账差多远。现状 `fresh_conv.tokens_used += len(full_reply)`（ws/handlers/chat.py:212）只记 output 字符数。两个失真源：① 字符≠token（中文≈1:1 但空格/ASCII 3.6:1 → 对本项目混排回复预计**高估 output 10–30%**）；② 完全不记 input，而玩家聊天 input=persona+记忆+全量历史逐轮重发（chat.py:167-176，无截断），20 轮会话 input 总量是 output 的很多倍。预期：20 轮会话中 tokens_used 记账值 ≈ 真实总 token（in+out）的 **≤15%**，作为成本口径不可用；且失真随会话长度增大（history 平方增长）。
- 方法：用 dev DB 真实回复样本（71/88 字符中文）校准 output 字符/token 比；复刻 handle_chat_msg 请求构造，模拟 5/10/20/40 轮会话（用户消息 15 字、回复 ~80 字、persona=median 208、memory 段 300 tokens），对比 accounted vs true。脚本：docs/research/scripts/e03_accounting_error.py
- 结果：① 真实回复 chars/est_tokens = 1.17–1.33（len() 高估 output token 17–33%）。② 会话级 accounted/true：5 轮 8.9% → 10 轮 6.9% → 20 轮 4.9% → 40 轮 3.0%。input 占真实总量 91–97% 且随轮次平方增长（无 history 截断）。
- 状态：done
- 结论：假设成立。现状 tokens_used 反映不到真实成本的 9%，且失真随会话变长恶化——**作为计费/预算依据不可用**。P1-1 计量必须从 SDK response.usage 落 input/output 双字段（含 cache_read/cache_creation 字段以备缓存后口径）。同时暴露一个独立成本问题：**chat_messages 无上限全量重发**（40 轮 input 85.7k tokens ≈ $0.086/会话 on Haiku）→ 衍生实验：history 截断/滚动摘要策略的省钱-质量权衡。
- 偏差与备注：真实回复样本仅 2 条 assistant（dev DB 小），字符/token 比不确定度大；②中合成回复恰为 ~1:1（纯中文），accounted≈true_out 是内容构造巧合，不影响 acct/true 主结论。

### E-04 互聊收尾 5 调用 → 1 合并调用的 token 数学
- 假设（实验前写）：为什么试——OPTIMIZATION_PLAN P1-1 提出合并关系更新进总结调用。读码后发现收尾实际是 **5 次调用**（extract_events×2 + update_relationship×2 + summary），dialog_text 重复发 3 次、SBTI 着色块（~200 tok）重复发 4 次、模板 system 重复 5 次。预期：设计单次合并调用（输出统一 JSON：summary+mood+双方 memories+双方 relationship），合并后收尾阶段 input 降至 5 调用方案的 **40–55%**，收尾阶段总 token（in+out）省 **40–50%**，且少 4 次串行 RTT（延迟收益另计）。
- 方法：用 est_tokens 复刻 5 调用现状的精确输入（真实模板+median persona+8 轮对话文本+完整 SBTI 块），对比合并 prompt 设计稿。脚本：docs/research/scripts/e04_merge_math.py
- 结果：现状 5 调用 in=3198/out≈600（total 3798）；合并 1 调用 in=1374/out≈600（total 1974）。**input 省 57.0%，total 省 48.0%**，RTT 5→1。Haiku 单场收尾 $0.0062 → $0.0044。
- 状态：done
- 结论：假设成立（input 43% 落在预测 40–55% 带内）。主要节省来源：dialog_text 3×→1×、SBTI 块 4×→2×（双居民各一份）、模板 system 5×→1×。收尾阶段占整场对话成本比例待 E-06 基线并入。前提是 E-05 证明 haiku 能稳定输出合并 JSON。
- 偏差与备注：模板骨架 token 用估计值（230/260/80），±15%；输出按"内容量等价"假设，合并后模型可能更啰嗦（E-05 实测校验）。

### E-05 合并调用 JSON 在真实 Haiku 4.5 上的可靠性
- 假设（实验前写）：为什么试——E-04 的省钱前提是目标模型（claude-haiku-4-5，项目生产默认）能稳定输出更复杂的合并 JSON（6 个顶层字段、嵌套双居民结构）。现状代码用 `re.search(r'\{[^{}]+\}')` 抓平 JSON（chat.py:187），嵌套结构必须换解析方式。预期：真实 haiku 5 次试跑 **≥4 次**输出完整可解析 JSON（json.loads 直接过或围栏剥离后过），字段齐全率 ≥90%；失败模式集中在 markdown 围栏而非结构错误。
- 方法：通过 Claude Code Agent 工具指定 model=haiku 跑 5 次相同合并 prompt（合成 8 轮对话），判定解析性与字段完整性。口径注意：Agent 工具有自身 harness system prompt，测的是"内容级指令遵循"，与生产纯 API 有环境差异（记入偏差）。
- 结果：**5/5 可解析**（json.loads 剥围栏后全过），顶层字段 4/4 齐全率 100%，嵌套结构（memories+relationship.metadata）5/5 完整，每居民 memories 2–3 条符合规格。失败模式与预测一致：5/5 都违反"不要围栏"指令带了 ```json 围栏（可一行代码恢复），无结构性失败。实际输出 1218–1669 chars（≈750–1050 est_tokens），高于 E-04 假设的 600。
- 状态：done
- 结论：假设成立（预测 ≥4/5，实测 5/5）。合并调用工程可行，解析器需要"剥围栏 + 平衡括号提取"（现有 `re.search(r'\{[^{}]+\}')` 必须换掉，它连嵌套 JSON 都抓不了）。用实测输出尺寸修正 E-04：合并后 total ≈ 1374+850=2224 vs 现状 3798 → **收尾阶段实际省 41%**（比 E-04 的 48% 低 7pp，仍显著）。
- 偏差与备注：n=5 样本小，置信区间宽（5/5 下限 ~57%@95%CI）；生产落地建议带解析失败重试 1 次的兜底（成本 +1 调用 × 失败率）。Agent harness 环境差异记为系统偏差，方向未知。

### E-06 全服成本基线模型（$/居民·天、$/100居民·月）
- 假设（实验前写）：为什么试——一切优化决策需要基线。频率模型（代码实证）：每居民日 = 1×plan（in≈900, out≤1200）+ ≤20×decide（in≈700, out≤200）+ 互聊若干场（每场 8 轮×2 人份 + 收尾 5 调用，E-02/E-04 实测）+ 玩家聊天另计。预期：15 居民全 Haiku 日成本 **< $1**；成本占比第一是互聊（>40%，因为单场 13 调用），第二是 decide（高频×20）；100 居民月成本落在 **$50–150** 区间（线性外推）；若换 Sonnet 全量 ×3–5。
- 方法：把 E-01..05 的实测尺寸 + tick/plan/decide 的 max_tokens 与频率参数（config.py:90-97）组装成参数化成本模型，输出敏感性表（互聊场次/居民/天 = 1/2/4，decide 实际 LLM 率 = 50%/100%）。脚本：docs/research/scripts/e06_baseline_model.py
- 结果：15 居民中位情形（2聊/居/天、decide 100% LLM、50 玩家条/天）= **$0.94/天 ≈ $28/月**；重聊情形（4聊）$1.35/天。100 居民同参数 **$6.23/天 ≈ $187/月**（区间 $107–268/月）。成本构成：**互聊 43% + decide 41%** + 玩家 9% + plan 7%。
- 状态：done
- 结论：假设**部分成立部分推翻**：①"15 居民 <$1/天"仅中位成立，重聊情形破线；②"100 居民月 $50–150"**低估了**，实际中位 $187（decide×20/天/居民 的权重被我低估）；③"互聊占比第一 >40%"成立（43%），但 decide 以 41% 几乎并列——**decide 是和互聊同级的省钱杠杆**，"无新事件跳过 decide/规则兜底"类实验优先级应提升。全 Haiku 下绝对成本尚可控；若默认模型换 Sonnet 直接 ×3（月 $560@100居民），分级模型是刚需门槛。
- 偏差与备注：绝对 $ 继承估计器 ±25%；decide 实际 LLM 率未实测（列了 50%/100% 两档），待后续实验用 dev 数据或代码路径统计校准；玩家条/天为假设参数。

### E-07 共享大前缀缓存在 Haiku 上的收支模型（E-01 后续）
- 假设（实验前写）：为什么试——E-01 证明现有 prompt 全部低于缓存阈值，唯一缓存路径是垫出 ≥4096 的前缀。但推导发现地板效应：命中一次的读成本 = 0.1×P ≥ 0.1×4096 ≈ 410 token 等价；若该调用原本的稳定内容 S < 410，缓存化必然亏。各流程 S 值：decide ≈ 400–500（模板+SBTI+persona 片段）、玩家聊天 ≈ 550（persona+memory+模板）、互聊轮 ≈ 350、收尾合并调用 ≈ 700。预期：**decide/互聊轮缓存化净收益为负或 ±5% 内**（不值得做）；玩家聊天勉强正（≤15%）；再叠加 per-resident 前缀 × 5min TTL 重写成本（1.25×），低频居民（tick 间隔>TTL）**全线转负**。总体预判：**在 Haiku + 当前 prompt 尺寸下，缓存不是可用杠杆**——这是负向结论实验，目的是把 B 类候选从路线图上砍掉或改造。
- 方法：参数化收支模型：flow×(S, V, 调用频率, TTL 命中率)，前缀 P=max(4096, S_global+persona)，输出各 flow 的 Δ$/调用与全服 Δ$/天。脚本：docs/research/scripts/e07_cache_econ.py
- 结果：hit=95% 时仍全线为负或近零：decide −195 tok/调用、chat_turn −295、player_chat −95、plan −45；唯一转正的是合并收尾 +55（但收尾频率低，实际 hit 到不了 95%）。全服 15 居民 hit=95% 情形 **Δ = −$0.13/天（更贵）**。对照组：若阈值是 1024（Sonnet 4.5 世代），全部 flow 转正（+189～+539 tok/调用）。
- 状态：done
- 结论：**负向假设成立——在 Haiku + 本项目 prompt 尺寸下，前缀缓存不是可用杠杆，应从优化清单剔除**。根因是 4096 最小前缀的读地板（0.1×4096≈410 tok）超过了各调用的真实稳定内容量。两个衍生方向留给路线图：① 分级模型与缓存的交互（1024 阈值模型上缓存全线转正，但单价 ×3，需要联合建模）；② 若未来给世界观/地图 lore 增料（内容驱动而非省钱驱动），缓存可让增料的边际成本降到 0.1×。
- 偏差与备注：模型假设 G 为纯垫料；若能把更多真实共享内容（地图/规则）挪进 G 则 S 上升、结论边界移动，但当前 decide 全部共享内容 ≈450 tok 已计入。TTL 重写成本未细算（会让结论更负，方向一致）。
