## 一、结论速览（TL;DR）

1. **现状基线**：15 居民 ≈ **$0.9±0.1/天（月 $26–30）**；100 居民 ≈ **$185±12/月**。成本构成：互聊 46% > decide 32% > 玩家聊天 11% > plan 7.5% > 进化+反思 4%（E-06/E-11）。绝对量级可控，**但完全没有计量和熔断，且三个结构性浪费点明确存在**。
2. **最大杠杆是"计划优先跳过 decide"**（E-09/E-10）：无事件 tick 上 LLM 复议 100% 只是橡皮图章（4/4 真实 haiku 试验），规则化跳过可砍 decide 调用 70–90% → **全服省 29–37%**，行为语义基本不变。
3. **第二杠杆是互聊管线修复**（E-02/E-04/E-05）：history 双注入（一行修复省对白输入 23%）+ 收尾 5 调用合并为 1（真实 haiku 5/5 可解析，收尾省 41%）→ 互聊整体约省 30% → **全服再省 ~14%**。
4. **玩家长会话用滑窗**（E-08/E-12）：`chat_messages[-10:]` 一行改动，40 轮省 60%、80 轮省 77%，短会话无感。
5. **缓存在当前形态下是负资产**（E-01/E-07/E-22，三重否定）：prompt 太小（中位 208 tok，距 Haiku 4096 最小缓存前缀一个数量级）、结构天天变、端点可能不透传。**从优化清单剔除**，不要花工程时间。
6. 叠加 1+2+3 后的理论稳态：全服总成本约降至现状的 **~45–55%**，且扩容悬崖同步从 ~86 居民推后到 ~200+（E-13：成本与吞吐是同一把刀）。

## 三、P1-1 落地建议

### 计量（E-23 设计稿，依据 E-03/E-19/E-22/F-02）

`llm_usage` 表字段：
```
id, ts, scenario(枚举: decide/plan/chat_turn/chat_wrapup/extract/update_rel/summary/
  reflect/evolution_shift/evolution_drift/evolution_sync/player_chat/player_wrapup/
  forge_*/sbti/sprite/skill_import), model, owner(system|user), resident_id, user_id,
conversation_id, attempt_no, parse_ok(bool), latency_ms,
input_tokens, output_tokens, cache_read_tokens, cache_creation_tokens,
source(usage|estimated), cost_usd(计算列)
```
要点（每条都有实验依据）：
- **按 attempt 记而非 success 记**（E-19：重试+解析失败让有效成本 ×1.05–1.14）；
- `parse_ok` 独立字段——付了钱走默认值兜底的调用是最该消灭的纯浪费（E-05：现 `re.search(r'\{[^{}]+\}')` 连嵌套 JSON 都解析不了，先换"剥围栏+平衡括号"解析器）；
- **usage 缺失的降级路径**：中转端点可能不回 usage 字段（修正-2）→ `source=estimated` 用 est_tokens 影子计量，字段结构不变；
- 现有 `Conversation.tokens_used += len(full_reply)` 直接废弃（E-03：只覆盖真实成本的 3–9% 且随会话长度恶化）。

### 熔断与路由（E-24 设计稿，依据 E-11/E-13/E-18）

- 预算层级：全局日预算（默认 = 基线 × 1.5 ≈ 15 居民 $1.5 / 100 居民 $9）、agent-loop 小时预算、per-user 玩家日预算（映射灵魂币）、forge 单请求上限（deep $0.15）。
- 分级动作：**80%** → 背景降频（tick 间隔 ×2、plan 转 48h）；**95%** → 背景规则化（P1 政策强制 interrupt=off、互聊暂停发起）；**100%** → 只保玩家可见调用，其余排队。降级路径全部有规则兜底（decide 走 plan、互聊直接不发起），不会白屏。
- 路由：背景调用锁 `claude-haiku-4-5`；玩家可见调用模型可配置（升 Sonnet 全服 +19%）。
- 吞吐守门（E-13）：并发利用率 >100% 时（≈86 居民@5% 互聊率），先扩 `agent_max_concurrent`/拆 worker（P0-3a），再谈成本。

### 顺手修的质量问题（研究副产物）

- 互聊回复 `max_tokens` 100→150、summary 150→200（E-17/E-26：真实输出最长 70 tok 且 50 字指令超标率 3/4，截断的半句话会进 history 污染后续轮）；
- 记忆条目入库限长（E-28：单条记忆无字数上限，会在后续所有检索注入中反复付费）；
- deep forge 的 extraction 输入加截断（E-20：12 条检索全文注入，尾部风险）；
- 行为设计问题：20 动作/日在 tick=60s 下 ~20–30 分钟烧完，居民"一天"半小时演完（E-11 副产物，成本与体验都建议改为按时段配给）。

## 四、预测校准复盘（研究方法的自我审计）

26 条假设：**14 条成立、9 条部分成立/部分推翻、3 条方向性推翻**。系统性偏差：量级预测高估为主（E-08/E-12/E-16 连续高估节省率，根因=忘扣固定成本分母，修正-1 后收敛），也有反向（E-27 保守过头、E-11 我和 Opus 都预测涨基线实际持平）。8 条口径修正全部当场落账（§0.5），2 条来自 Opus 评审（端点存疑、基线漏项），1 条来自执行中自查（动作帽 vs 作息门控）。
